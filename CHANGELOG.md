# Changelog

All notable user-visible changes are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/) once it reaches 0.1.0.

## [Unreleased]

### Changed

- Implicit methods (`backward_euler`, `trbdf2`) factorise with an LU of their own on the matrix's symmetric pattern (ADR 0087): about 3× faster per step on 2D grids (Gray–Scott at 128 × 128 with TR-BDF2: 165 ms a step, from 520), the same in 1D. Their results change in the last bits.
- Wiring a view while paused or before running records the current sample of what it reads, instead of leaving it empty.
- An input over a table that has its own `start`, rules or edges is now matched to its rows by id (NaN for a row the input lacks), instead of being refused; only a table with none of these follows its input's rows.
- A recorded-data block, `at_times` and `at_samples` count a step whose time is within rounding of a sample's as at it. Before, steps summed from `dt` could fall a hair short (2.4999999999998 for 2500 steps of 0.001) and take the sample a step late. In models with data, a sample can now take effect one step earlier than before, so their results can change slightly (not only in the last digits); they stay exact within this version on any machine. Run files made earlier replay with that difference, and say so (below).
- Run files and `run --format json` output record the SimSandbox that made them (`"made_with": "simsandbox 0.0.1"`). Replaying a run made by another version, or before this was recorded, warns that results can differ where the changelog says.

- The study form in the app shows no "from", "to" or "points" for a study whose points arrive through its inputs, and switching a study to that design drops them from the file: another model sends its values.

- In the app, a model whose steps are rounds (maps that never read time, with an end, such as the search example) runs its rounds as fast as it can instead of one per simulated second, stops when a round changes nothing, and starts again from round 0 when a value changes. Its toolbar shows the round in place of Run, Pause, the speed and the time. Block types can say they never read time (`Block::reads_time`).

- Typed equations: `prev` and `next` of an array over two axes must name the axis (`prev(u, x)`); before, they ran along the first.
- Typed equations: each `grid` line is an axis of its own (ADR 0080). An axis's output is over that axis alone: Gray–Scott's `gs.x` and `gs.y` are 128 values each instead of 128 × 128 (views show the same pictures). `state T[x]` in a block that also has `grid y` now declares T over x alone instead of being refused. Results of every example are unchanged.

- A study block no longer runs its points once on inputs of zero when a run starts; the results are unchanged.
- Headless runs of models that feed each other on their own clocks are faster (1.3–1.6× for two mid-size grids): they keep their threads for the whole run. Results are unchanged bit for bit.
- Very large models (a million state values or more, such as a 1024 × 1024 grid) run several percent faster with Euler and RK4: their state updates use several cores. Results are unchanged bit for bit.
- `sum` and `mean` over more than 4096 cells add in fixed chunks (ADR 0077): about 4× faster, on several cores for very large arrays, and the same bits on any machine. Their last bits differ once from earlier versions (Gray–Scott's `v_mean` by 7 parts in 10^15); run files of such models recorded earlier no longer replay bit for bit. A mean or sum in a grid model's rates no longer slows the rest of the evaluation.
- Headless runs of models linked one way (a model feeding another that does not feed it back) are faster: each runs ahead on a thread of its own, its samples passed on; results are unchanged bit for bit. A chain of five small models runs about 2.5× faster.
- Models on their own clocks run faster in the app (and headless with inputs, probes or run files): the simulator keeps its threads for the whole run instead of starting them at each instant. Two mid-size models are about 1.5× faster; results are unchanged bit for bit.
- Large typed-equation models run 10–20% faster: their state arrays are read, and their rates written, where the integrator keeps them instead of being copied at every evaluation. Results are unchanged bit for bit.
- Large array models use several cores within one model, with the same results bit for bit: cell-by-cell work runs in chunks, one per core, when its arrays are large enough for sharing to pay (each part measures itself). A 512 × 512 Gray–Scott grid runs about 1.7× faster on 4 cores; smaller grids run as before.
- Faster runs, with the same results bit for bit: fused groups about 2.7× (no allocation at each evaluation), small models about 1.8× and large grids about 1.25× (integrators keep their working arrays), models on their own clocks with links about 9× (the core count was asked of the system at every instant). A block's `Equations::rhs` must write every element of `dx`.

- Models on their own clocks step on several cores between instants, in the app and headless, with the same results bit for bit; small models stay on one core. Two Gray–Scott models side by side run in about two thirds of the time they took. Headless, models that no link joins run apart from start to end, each group on a thread of its own: two unlinked models take about the time of one.

- A block picked inside a model expanded in place shows its values in the Inspector, as when the model is opened; before, nothing showed.

- Parameters can be driven by wires (ADR 0075): a connection may end at any block's parameter (`"to": "decay.k"`), a used model's declared parameter (`car1/mass`) or a study's (`curve.m`), and the signal replaces the value: followed at every evaluation, read at the start for starting values, a study running again when it changes. The parameter keeps its own value, used again once the wire goes. `check` lists what is driven. Outputs declare which parameters they read at once, so loops through driven parameters are found and solved like any other. In the app, drop a wire on a node's value to drive it and drag it off the value's dot to give it back its own value, also from outside a model expanded in place onto a value it exposes; a driven value says where it comes from (`from push.F`), stays shown on a closed node, and has no field or slider in the Inspector and Controls. New example: the forced spring.

- Exposing a model's ports and parameters (ADR 0074): inside a model, opened or expanded in place, a click on a block's port exposes it to the models using this one (an input they wire, an output they read), and a click on the ring beside a value makes it a parameter of the model that each use or study sets; a second click hides it again. Exposed ports are ringed and exposed values say what they are exposed as (`m as mass`). A wire from outside an expanded model to a port it exposes goes to the use's port. The used model's "Show a port" list and the blocks' "Offer … to models using this one" items are removed. The Platoon's follower exposes its `lead` input instead of holding an input block, with the same results; Duplicate feeds a copy's inputs from outside as its original's are.

- A study's parameters are its model's declared parameters (ADR 0074): the model's values are their defaults, each study sets its own (`"params"` on its entry), shown on its node and in the Inspector and pinned as sliders. "Study this model" carries a use's values over. The resonance examples declare the spring's `c`, `m` and `w` as parameters and have no input blocks: their studies set `c` and `m` and vary `w` (outputs `curve.w`, `map.w`, `map.c`).

- Plot axes, heat-map and surface scales and cut lines show units (`car.v [m/s]`, `t [s]`); units are printed in SI form (`kg/s`, `1/s`).
- The "Values" view is named `plot.values`, like the other built-in views.
- The selection on the diagram stays when an edit keeps its blocks (a study's form, an offered output), so the Inspector's buttons and choices can be used one after another.
- A block picked inside a study shows the studied model's values in the Inspector, editable (a change edits the model, with the usual question where it is used elsewhere); values typed on nodes inside a study now apply. The model tree lists a study as "study of cruise" with its model's values nested.
- A study's stacked cards sit below its node, narrower, clear of the ports.

- Offering outputs to models using this one (ADR 0073): the Inspector's Model section lists them and offers more; a block's menu offers its outputs only inside a used model ("Offer v to models using this one"). A used model's "Show a port" list no longer repeats a signal a declared output already shows (the Platoon's followers show `v`, not also `car.v`), and marks inputs and outputs in words instead of arrows that did not draw.

- A study's node is drawn as a stack of cards with its own header colour and the inner outline used models have (a model inside, to open), titled "study of cruise · 20 runs".

- A model with nothing in time (formulas and studies only: no states, tables, data, clocks or scheduled inputs) is evaluated in the app, not run: once when opened and again whenever a value it reads changes, the toolbar saying "Evaluated, not run in time" instead of showing Run, the time, the step and the rewind bar (ADR 0072).

- Sweeps and experiments are studies (ADR 0071): a file's top-level `sample` is refused, saying to put the model under `models` with a study block over it; the older `controls.sweep` is dropped with a warning. A model with no states is no longer swept over its first parameter: it runs in time, its formulas constant unless their inputs change. The app's sweep bar, its `grid.` signals and its unordered samples are gone: a study's results are fields like any other. `check` no longer reports `experiment` or `swept`; `run` writes a row per run for a model whose only runs are its studies. A study's results leave out its model's input blocks.
- The resonance examples are a spring model and a study of it: the curve (600 values of w, damping and mass as sliders feeding the study's inputs), the map (a grid over w and c, its 2D results drawn as a heat map, surface and cuts) and the samples (a Sobol study drawn cell by cell).
- Python: `Model.sweep` and `Results.series` are removed; `keep: "series"` is refused (Q52).

- A study names its model as a use does, `"model": "cruise"` or `"file": "car.ssbx.json"` on its entry (no longer in `settings`), and its node opens to that model to see and edit it, with the same choices as a used model's.
- `controls.plots` is removed from the format (it did nothing since ADR 0063); a file that still has it loads, the key ignored.
- The examples are written as SimSandbox now builds models, with the same results: values and starts once, in the typed equations; units on the resonance and predator–prey formulas; no `controls.plots`, default methods or unused `run.dt`. The Platoon is listed as a model defined once and used three times.
- A model with no states that reads an `input.file` is no longer swept over its first parameter by default: it runs in time at its data's samples (ADR 0067 step 4).
- A model used by another runs as written (ADR 0070): its own `sample` is no longer run at each delivery but ignored with a warning; study it with a study block. A file's `sample` is the study of its model: sweeps and experiments run through one runner, `check` reports both under `experiment` with `each_run`, and a model whose only runs are its studies writes a row per run.
- Subsystems are replaced by models defined in the file (ADR 0068): `subsystems` is refused with how to write it under `models`; "Make subsystem" is "Make model"; a model's inputs are input blocks and its outputs are offered from a block's menu ("Offer X as an output"); `render --diagram --inside PATH` (and Python `render(inside=)`) draws a used model's inside; Python `Model.group` makes a model. The Platoon example defines its follower once. Problems inside a used model are reported where they are written (`models.follower.blocks[0].equations`). "Edit…" on a block inside a used model opens its equations.

### Added

- Networks from files in typed equations: `start nodes = file "nodes.csv"` starts a table from a CSV file (an `id` column, and a column per quantity, with units in the header if wanted); an edge table's file has `from` and `to` (node ids); `param g[wires] [S] = 0.001` is a value per row; `outflow(I, wires)` sums a flow along edges onto their ends; `param m[k] [kg] = file "masses.csv"` reads an array parameter's values. The files count in the model hash. Example: `examples/networks/bridge.ssbx.json`, a Wheatstone bridge.
- `dx/dt = 0` (a right side of exactly zero) balances in any unit.
- Built-in examples may read files: the app opens such an example from a folder holding them, and Save as writes them beside the saved model. "A Wheatstone bridge (a network from files)" is in the Examples menu.
- **Fill the past** in the run bar: something wired to a view during a run, which had no past until Restart, is filled by running again from a snapshot with the input as recorded, giving the same numbers as a run that recorded it from the start; the run then carries on from where it was. Needs the recorder. Rust: `Session::has_gaps` and `Session::recompute`.
- `plot.mesh` cuts a 3D mesh by a plane in any direction (along x, y or z, or any normal, with a slider), drawing the section flat; the cut is saved with the view as `{"cut": {"normal": […], "at": …}}`. `plot.xy` draws quantities over a table's rows against each other, cell by cell, paired by id.
- Strategy helpers write refinement over any number of parameters, in one form: `{"kind": "refine", "params": [{"param": "f.u", "range": [-1, 1]}, …], "result": …}`, Python `Model.refine(target, {"f.u": (-1, 1), "f.v": (-1, 1)}, result)`, and the app's "Search…": a mesh of simplices over the parameters (segments over one) refined where the result changes. `param` and `range` alone, and Python's `refine(target, param, range, result)`, are replaced by it.
- In the app, meshes are drawn by the GPU (wgpu) with a depth buffer; headless renders draw the same triangles with egui.
- `plot.mesh` (ADR 0086): a quantity over a mesh's cells or points drawn on the mesh, cells filled in 2D and the outer surface in 3D, turned with the mouse; a model with a mesh opens on it. Each table of cells is an output carrying its cells' corners. A profile draws a quantity over a table's rows against another over the same table, paired by id.

- Views draw fields of any number of axes (ADR 0086, ADR 0081 stage 3): a heat map, surface or contour shows two of a field's axes and a profile one; each axis left over is picked at a place with a slider, reduced (mean, minof, maxof, sum) or shown as facets, and the choice is saved with the view. Views may bind fields over three or more axes and rows in model files.
- Time on meshes (ADR 0085 step 3): continuous states over a table's rows (`du/dt = …` over cells, integrated by any method with the mesh fixed within a step and refined between steps); `outflow(F, f)`, each cell's net outflow of a flux written per side; `across(u, f)`, the value across a side (the cell's own on the boundary); implicit methods get a Jacobian as sparse as the mesh; starting values may read a starting mesh's coordinates.
- Refinement of meshes (ADR 0085 step 2): `split c where cond` bisects simplices (triangles, tetrahedra, `simplex d`) without hanging points and splits boxes (quads, hexahedra, `box d`) into 2^d, neighbours at most one level apart; `merge c where cond` gives the parent back. Transfers: `copy` and `share` on split, `mean`, `sum` and `copy` on merge, `mean` for new points, or a value. A study's points can be refined over two or more parameters.
- Meshes from Gmsh files (ADR 0085 step 1b): `start c = file "part.msh" at x, y, z` reads an ASCII `.msh` (versions 4.1 and 2.2) into a table of points and cells; several cell tables of different shapes may start from one file. A relative path is from the model's folder, and the file is part of the run hash.
- A model loaded with a folder (`Session::load_in`, the app) now builds its blocks in that folder, so a block that reads a file while it is built finds it as under the headless tools.
- Meshes in typed equations (ADR 0085 step 1a): `cells c of pts: triangle` (segments, triangles, quads, tetrahedra, hexahedra, prisms, pyramids, d-simplices, d-boxes) over a table of points, `start c = grid x 0 .. 1 by 8, y 0 .. 1 by 8`, `sides f of c` kept with stable ids, and geometry: `corner`, `centre`, `measure`, `normal`, `inner`, `outer`, `boundary`. Cells, sides and edges may hold states.

- A memory budget for recordings (ADR 0062 step 5): one app setting, 1024 MB by default and kept between launches, under "Memory…" in the toolbar, shared by rewind's snapshots, the history, probes and filters (a quarter each by default; a recorder or probe with a size of its own keeps it). The toolbar says when recordings hold more than the budget and which holds most. Headless: `simsandbox run --probe … --memory MB`, Python `Model.run_probes(memory=MB)` and `ProbeRun.memory`. Nothing changes at the default.

- Strategy helpers (ADR 0078 step 5): Python's `Model.minimize`, `Model.fit`, `Model.refine` and `Model.continue_` write a study and a strategy model (pattern search, Levenberg–Marquardt, refinement, continuation) that drives it, for any number of parameters, from a study, a used model or the whole model; the app's study form does the same under "Search…". The strategy is an ordinary block that can be opened and changed.
- Typed equations: an array state's starting value may read an array parameter (`state x[p] = x_start` with `param x_start[p]`).

- Example "Finding where a state's fate changes (refinement as a model)": a study runs a bistable state from each of a table of starting values, and a refining block splits the intervals whose ends settle on different branches, bracketing the boundary between the two within 0.001 in 18 runs.

- Edge tables in typed equations (ADR 0079 stage 2): `edges segs of pts` joins rows of a table, `start segs = chain` joins each starting row to the next, `from_end(x, segs)` and `to_end(x, segs)` read a quantity at each edge's ends, and the rules `split segs where …` (a new row in the middle of each edge) and `merge segs where …` (an edge's two rows into one) change them between steps, each column filled by `copy`, `mean` or an expression. Removing a row removes its edges.
- With them, refinement of a study over one parameter: a model that splits the intervals where a study's results jump, the study running only the new points.

- Studies over a table's rows (ADR 0079 stage 1d): a study with `"design": "rows"` runs one point per row arriving through its inputs, and gives each result as rows with the same ids. Each row's results are kept by id, so only new or changed rows run again. The app's study form offers it as "a point per row of a table".

- A table's rows are recorded and written by id (ADR 0079 stage 1c): `run --format json` gives each quantity over rows under `over_rows` (versions, ids, values per row); CSV gives a column per id (`pop.size#7`), NaN where that row is not there; a probe writes `<stem>.<field>.csv` with a line per row per sample (`t,version,id,value`); Python gives `Results.over_rows` (and `Probe.over_rows`) as `Rows`, with `of(id)` and `by_id()`. JSON output has the new key `over_rows` in every run (empty without tables).

- Typed equations: a quantity over a table's rows is a port carrying the rows' values with their ids and the table's version (ADR 0079 stage 1b). Wire it to a block with `table q` and `input size[q]`: `q` follows those rows by id at the same instant, its states keeping each row's value by id and starting new rows from their starting values. Rows are recorded by id (below).
- Outputs of varying length (rows, populations) may depend on inputs at the same instant: the simulator computes them after their sources. A loop of such dependence through them is refused with an explanation.

- Ports of any number of axes (ADR 0081): a typed-equations quantity over three or more axes (up to 8) is a port, wired, recorded and written out; a study's vector result over a grid of two parameters is a port of three axes. Ports name their axes. `run --format json` describes every shape by its axes (name and length); CSV names a cell of three or more axes by its places (`q[1,2,3]`); Python returns `(rows, nk, …, n1)` arrays and `Results.axes(name)`.

- Tables in typed equations (ADR 0079): `table pts`, `start pts = 5`, states with a value per row, and rules between steps (`remove pts where …`, `add pts from … where …: …`). Rows keep their ids (`id(pts)`, `of(T, i)`, `rows(pts)`), and rewind and run files keep them. In maps; their values are not ports yet.

- Example "Following a branch through hysteresis": continuation written as a model. Each run starts where the last settled, at the next value of a parameter, so a bistable state follows its branch to the fold and jumps, tracing a hysteresis loop.

- Example "Fitting a model to measurements": Levenberg–Marquardt written as a model fits a damped oscillator's stiffness and damping to 20 measured positions, reaching the least-squares fit SciPy finds. `rcond(A)` in typed equations, how far a matrix is from singular. `input.file` takes its samples as CSV text in the model (`"data"`), so a small data set travels with the model.

- Studies give a vector per run (ADR 0080): `at_times(e, t1, t2, …)` and `at_samples(e, data)` in `reduce`, the latter at each sample of a recorded-data block, for model-minus-data residuals. Such a result is over its own axis and the runs, read in typed equations as `input res[obs, run]`.

- `solve(A, b)` in typed equations (ADR 0080): `A` over two axes of the same length, `b` over one of them; the result, over the other axis, solves `sum(A*x, j) = b`, the same bits on any machine, NaN if `A` is singular. `dd(T, x)` is the derivative along a named axis, as `ddx(T)`.

- Named axes in typed equations (ADR 0080): quantities over some of a block's axes (`param m[k]`, `input r[i, k]`, `state T[x]` beside `grid y`), quantities over different axes combined over all of them (`a[i] + b[k]`), `sum(T, k)`, `mean`, `minof`, `maxof`, `argminof` and `argmaxof` along one axis, and `on(T, a, b)` to read an axis as another of the same length (`sum(J*on(J, p, q), r)` is JᵀJ).

- Search strategies as models (ADR 0078): a study's points can come from its inputs (`"design": "inputs"`), and it reruns only points that changed; maps can use grids and array states; a pattern-search example tunes two cruise-control gains (`cruise-search.ssbx.json`).
- `simsandbox run --signals NAMES --every N` and Python `run(signals=..., every=...)`: keep only the outputs named and every N-th step (and the last), for less memory and time; the values are the same. `--model` on a model using models records only that model.
- A model can expose its blocks' inputs (`"inputs": [{"name": ..., "to": [...], "unit": ...}]`, ADR 0074): signals with no default, wired by every use and study, without input blocks; a use that leaves one unwired is refused, naming it.

- A study selected on the diagram has a form in the Inspector: its design, a row per parameter it varies (chosen from its model's parameters, with range and points), count and seed, replicates and seeds, its named results, and the number of runs; the sample as JSON stays one click away.

- View "Values" (`plot.values`): the newest value of each chosen signal as a number with its unit, and lines of cells (a study's results) as a table. The tuning example shows its best gain, reach and peak with it.

- A model whose studies take a while no longer freezes the window: opening it, and checking a diagram edit, build it without running its studies; the worker runs them first, showing their progress ("studies about to run", then "study: k of n runs"), and anything the window waits for (Save, closing) gives them up and runs them again after (ADR 0071).

- A study running in the app shows its progress ("study: k of n runs"); changing a parameter or input it reads, Pause or Run gives it up and runs it again from the new values, so the results never depend on timing (ADR 0071).

- "Study this model" on the canvas background studies the whole model: its blocks move into a new definition used in their place, with a study of it beside (Python `Model.as_study(("spring.w", 0, 3, 600))` or `as_study(sample={...})`).

- A study over a grid of two parameters gives 2D results (`n1 × n2` cells) with both parameters as coordinates, so heat maps, surfaces, contours and cuts read them directly (ADR 0071).
- `plot.xy` takes lines of cells, such as a study's results, for `x`, `y` and `colour` and draws them against each other cell by cell (preset "Cell by cell"); the tuning example shows reach against peak, coloured by gain.
- Example "Tuning a controller's gain": a study of the cruise-control model, defined once in the file, over the integral gain; a formula reads the study's arrays and picks the fastest gain whose peak stays under a limit you can slide.
- Time from data (ADR 0067 step 4): a model with no states that reads recorded data steps at the data's own sample times, even irregular ones, and without `t_end` ends at the last sample; a used model on new data is evaluated at its data's samples too; a use may step at listed times with `"clock": {"times": [0.5, 1.2, 4]}`.
- Studies in the app (ADR 0070 step 5): "Study this model" on a used model's node adds a study block over it (Python `Model.study`); the Inspector edits a study's model and sample; a model holding a study opens on a profile of its results; study nodes say what they study and how many runs. A study's points file and its model's data files are part of the run hash.
- Point ids (ADR 0070 step 4): a points file may give each point an `id`; per-point seeds mix in the id rather than the row, so a point's random draws do not depend on where it is in the file (unchanged for designs without ids). The points file is now part of the run hash.
- Study arrays in formulas (ADR 0070 step 3): study outputs are lines of cells; typed equations number them with `grid k = n` and read them as arrays; `argmaxof`, `argminof` and `at(T, i)` with a computed cell (`at(w, argmaxof(amp))`). Comparisons `<`, `<=`, `>`, `>=` (1 or 0) in every expression. `reduce` results are any expression of reductions (`max(car.v) - final(car.v)`); `first_time(e)` takes any condition.
- Study blocks (ADR 0070): `{"type": "study", "settings": {"model": "cruise"}, "sample": {...}}` runs a model (a definition or `settings.file`) at each point of its sample and outputs arrays with one value per run; the model's input blocks are its inputs, so studies feed and nest in other models.
- `reduce` in an experiment (ADR 0067): named results, one per run, such as `"v_max": "max(plant/car.v)"` or `"settle": "first_time(abs(cruise.e) < 0.1)"` (also `final`, `mean`, `min`, `amplitude`, `period`); signal expressions read paths such as `plant/car.v` as one name.
- Experiments over any model (ADR 0067): a `sample` on a model that runs in time, or uses models, now runs the whole model at each point, in parallel with the same results on any number of cores, keeping each output's final value (or each run, `keep: "series"`); points set parameters by path or declared name, or come from a CSV (`design: "file"`); `seeds: "per point"` and `replicates` for Monte Carlo. `check` describes it; Python `Results.series`.
- Models that use models take inputs, probes and run files (ADR 0066 step 5): `run --inputs`, `--probe`, `--save-probes` and run files work on them, with keys and signals by full name (`slow/u.y`); Python `run(inputs=...)` too; a run file notices when a used file changed.
- Array parameters and neighbours in typed equations (ADR 0069): `param m[k] [kg] = 1000` is a value per cell, each its own parameter `m[0]`, `m[1]`, …; `prev(v)` and `next(v)` read the neighbouring cells, beyond an end the edge's value (`edge v: k- = lead`). The Platoon written as one array block gives the same numbers as its three cars.
- Duplicate (ADR 0069): a block's or a used model's menu, or Ctrl+D, copies the selection beside itself with its values and the wires among the copies; Python `Model.duplicate`.
- Expand in place (ADR 0066 step 4d): "Expand in place" on a used model's node shows its blocks in an outline coloured by its clock, wired through, with neighbours making room; edits there change the model it uses, asking where as when it is opened. Expanded uses are saved in `controls.expand`. Headless: `render --diagram --expand PATHS`, Python `render(diagram=True, expand=[...])`.
- Models defined in a model file (ADR 0068): a `models` section holds definitions written like model files, used from `blocks` by name (`{"name": "front", "model": "wheel"}`), any number of times. Their inputs are their input blocks and their outputs their declared `outputs`. Wired, a model with no `run.dt` of its own runs on its user's clock. Uses set start states inside by path (`starts`). "Make a local copy" now adds such a definition. `check` lists `definitions`; Python: `Model.define`, `add_model(model=...)`. Saving writes `run.dt` only when the file had it or it differs from the default. In the app, "Make model" moves a selection into such a definition; editing inside a definition used several times asks whether to change every use, make a new file or make a local copy; a definition moves to its own file ("Move to its own file…") and a used file into the model ("Put in this file").
- Models that use model files (ADR 0066): an entry of a model's `blocks` may name a `file` in place of a `type`. The used model runs on its own clock (`clock: {"dt": …}`, or the file's `run.dt`), with parameter values for this use only, and may itself use files, to any depth. With `"clock": "shared"` it runs on the using model's clock instead, flattened in like a subsystem, so wires go straight into its input blocks and the solver fuses across the boundary. Any model file can be used either way; wires reach input blocks and outputs at any depth, and a use's `params` reach any depth by path (`plant/car.m`), each a number or a formula of the using model's declared parameters. Names inside carry the path of uses (`vehicle/plant/car.v`). Probes link one model's output to another's input block at any depth, sampled and held. Clocks interleave in exact ticks, however rarely they meet, and each model stops at its last step at or before the end time. `simsandbox check` and `run` handle such models (`run --model NAME` for CSV). Python: `Model.add_model` (with `shared=`), `Model.link`, and `Model.run()` returning `Composed`. Opening them in the app comes later. Models without states run on new data: evaluated whenever a link delivers a sample, or, with a `sample` section, running their whole sweep then. A model with nothing in time (a pipeline of models without states) is evaluated once, in link order. `render --diagram` draws each used model as a node showing its clock and file. A model file may declare the outputs it offers (`outputs`), which users reach by name (`plant/speed`); a used model's node shows its inputs, declared outputs and what is wired. The app opens and runs them, with views, sliders and rewind, each model on its own clock. In the app, opening a used model shows its inside (read-only for now), "Show a port" in its menu finds any port inside by path, and the Inspector shows parameters as a tree by path. A use may replace the files of models used inside it, for that use only: `"files": {"plant": "car-2.ssbx.json"}` (Python: `add_model(..., files=)`); `check` lists them as `replaced_files`. In the app, editing inside a used model asks where the edit goes: the original file, a new copy with its own file, or a local copy written into the model (`"model": {…}` in place of `"file"`); Save writes every file edited, and undo covers them. Wires drawn between models on different clocks become probe links into input blocks; "Add model…" in the canvas's menu uses a model file.
- Recorded data as an input (ADR 0063): an `input.file` block reads a probe's file, or any CSV or `.npy`, from the model's folder and gives its columns as outputs over time, held between samples or interpolated linearly. Units come from `name [unit]` in a CSV header or the block's settings. Name the file in the Inspector (typed or chosen). A probe's file read back drives a model exactly as the probe did. The data file's contents count in a run file's model hash.
- Python: `Model.folder`, set by `Model.load` and `Model.save`, is where a model's blocks read their files.
- Probes can write their file as they record ("write as it records" in the probe's settings, `"stream": true` in the file): every sample goes to disk, buffered and flushed about every 2 s, without being held in memory; rewind cuts the file back.
- A probe's Keep can be "thinned past N samples" (`"keep": {"samples": N}`); the default, 100 000, is shown and editable.
- A probe can feed a block of its own model (ADR 0063): drop a probe's output on a block's input and the block reads that signal as the probe samples it, held between samples, with no delay, like a sensor read by a digital controller. In the file: `{"from": "probe:sensor.car.v", "to": "cruise.v"}`. Such a probe is part of the model: changing when it records rebuilds and restarts the run, and run files notice it.
- Probes on the diagram (ADR 0062): "Add probe" in the Diagram's menu adds a probe node; drop outputs or filter outputs on its `record` input to record them, delete a wire to stop. Double-click it to set when it records, how long it keeps samples and its file. Changes apply without restarting the run, and undo works as for filters and views. Runs › "Save probe data" writes the probes' files beside the model.
- Probes have outputs (ADR 0063): wire one into a view to show what the probe recorded, when it recorded it, or into a filter's input to compute on the probe's samples (`probe:NAME/signal` in the file; a filter gets `"from": {"car.v": "NAME"}`). A filter may read several probes: by default it runs where their times pair; "Run when any input records" (`"when": "any"`) runs it whenever one of them records, with the others' latest values. A filter's outputs are bound by name wherever it runs. One plot can show curves from the model and from probes at different rates; signals from different sources are paired only at times both recorded.
- The model's every-step recording now keeps only what views and filters read from the model, so unwatched outputs, large grids especially, take no memory. A signal wired to a view during a run starts from then; restart to see it from t = 0. Probes can record any output, not only those in `controls.plots`, which no longer limits anything.
- Probes in model files (ADR 0062): `controls.probes` entries record chosen signals and fields (`"record": ["gs.v"]`), every N steps, every Δt of simulated time or at listed times (`"every": {"seconds": 50}`), keep them thinned, the newest N or all (`"keep": {"last": 100}`), and can write files (`"to": "pattern.csv"`): a CSV of time and signals, and a NumPy `.npy` file per grid or point field beside it. `simsandbox run FILE --probe NAME` prints one probe; `--save-probes DIR` writes the probes' files. Python: `Model.add_probe` and `Model.run_probes(save=...)`. A probe with bad settings is dropped with a warning; the file still opens.
- Example "Gray–Scott spots (reaction–diffusion on a 2D grid)": two chemicals on a 128 × 128 periodic grid; from two seeds, spots grow and split. Sliders for F and k change the pattern.
- 2D grids in typed equations: two `grid` lines make a grid, arrays are written `T[x, y]`, `lap(T)` sums the second derivatives along both axes, `ddy(T)` differentiates along y, edges are set per axis (`edge T: x periodic, y- = 0`), and `at(T, i, j)` reads one cell. The heat map shows them with both axes as coordinates.
- Implicit methods `trbdf2` (second order) and `backward_euler` (first order) for stiff systems such as diffusion on fine grids: they stay stable at steps far beyond what `rk4` allows (a 0.05 s step of an 800-cell rod takes 0.25 ms instead of 5 ms with the substeps RK4 needs). Every continuous block and fused group can use them, and runs still replay exactly after a rewind.
- Example "Typed heat equation (arrays on a grid)": the heat rod in four lines of typed equations, verified against the exact solution of the heat equation.
- Arrays in typed equations (ADR 0060). Declare a line of cells with `grid x [m] = 0 .. length, 50`; then `state T[x] [K] = expression` has a value per cell, and `dT/dt = alpha*lap(T)` is the heat equation. Set the ends with `edge T: x- = left, x+ gradient = 0` or `edge T: x periodic` (insulated if not given). `lap(T)` and `ddx(T)` are stencils; `sum`, `mean`, `minof`, `maxof` and `at(T, i)` give one value; `spacing(x)` is the cell width. Arrays are grid outputs with the axis as their coordinate, so the heat map and profile views show them, and `input q[x]` takes a grid from another block. Units are checked throughout. A typed heat rod runs as fast as the built-in one.
- Inputs (ADR 0058): `input.value` and `input.pointer` blocks are values set from outside a running model, wired like any block (settings `unit`, `min`, `max`). Bind them in `controls.inputs`: two keys drive a value (`{"driver": {"keys": ["ArrowDown", "ArrowUp"]}}`, optionally at a `rate` per second), and a view feeds a pointer (`{"hand": {"view": 0}}`): pressing on `plot.xy` or the pendulum view then sends `x`, `y` and `down` instead of panning. New examples: "Drag the bob" and "Steer the car with keys". `plot.xy` has two new styles: `reach` (always show at least that far either side of 0) and `equal_scales`.
- Every change made during a run (keys, pointer, sliders, typed values) is recorded at a step boundary. After a rewind, running on replays it exactly ("Replaying input" in the toolbar); new input from then on starts a new branch. `run.inputs` in the model file is a default schedule of changes (`{"t": 5, "set": "push.y", "to": 40}`) applied in every run.
- Run files (ADR 0059): Runs ▸ "Save run…" writes `<model>.<run>.run.json` beside the model with the run's schedule, recorded input, seed, settings and the model's hash. The Runs menu replays a saved run (warning if the model changed since) and can make a run, or the current one, the model's schedule. Opening a run file (or dropping one on the window) replays it.

- Units in typed equations (ADR 0045, ADR 0049): write a unit in brackets where a name appears, `input F [N], v [m/s]`, `param m [kg] = 1000`, `state v [m/s] = 0`, or at the end of an equation for its left side, `E = m*v^2/2 [J]`, `dv/dt = (F - c*v)/m [m/s^2]`. ### Fixed

- Outputs of states over cells, sides or edges (ADR 0085) gave the cells' corner ids instead of the states' values, in views and in `run` output.
- A block picked on the diagram inside a used model now shows its values in the Inspector's selection (it showed nothing).
- Undo on the canvas kept parameter values moved since the edit only for parameters the file wrote; it now keeps them for parameters left at their defaults too, where the block's definition is unchanged.
- A model file whose controls held only a layout, open nodes, input bindings, probes or a recorder lost them when saved.
- A model no longer shows "unsaved" right after opening: the window fitting its panes to their contents is not counted as a change, and is not saved.
- Turning off a slider in a model saved before pins (such as the platoon) also unpinned the value. Such files now get their pins when opened, reported as a conversion.
- A popped-out tab froze the main window while the main window had focus (Linux): popped-out tabs now draw on their own.
- Turning the only plot into a tab of its own no longer removes the Views tab, so the plot can be tiled back after closing its tab.
- Popping out a tab no longer waits for vsync, which could stall the main window on Linux (Wayland).
- A value typed on a block that was not running yet was ignored; it now goes into the pending edits.
- An arrow that the app's font lacks showed as a box in conversion labels and some messages.
- Numbers in model files are read back exactly as written; before, some values came back one unit in the last place off, so a saved model could differ slightly from the one that was saved.
- App: a sweep that reaches an infinite value (the resonance example swept over `spring.c` from 0) no longer crashes; plots leave a gap at infinite or NaN values. Choosing a sweep parameter uses its slider range when it has one.

### Changed

- A probe keeps samples in memory only when a view or filter reads it or it writes a file when the run ends; otherwise Keep has no effect and the probe holds nothing.
- Hide data keeps probes that feed blocks of the model on the diagram: they are part of the model.
- The app opens maximized, on a landing page: "New model…", "Open…" and the examples, each with its description on hover (it used to open the Lorenz example). A file given on the command line still opens at once. F11 toggles full screen.
- Rewind is now opt-in (ADR 0064): add a recorder on the Diagram ("Add recorder") and the rewind bar appears; its settings say how often it saves the model's state (every 10 steps) and how much memory it may use (256 MB). Without one, no memory goes to rewind and the bar is hidden. Restart and replaying saved runs work as before. The "Drag the bob" and "Steer the car with keys" examples include one; add one to a model you want to rewind (`"recorder": {}` in `controls`).
- Rewind keeps far more of a run in the same memory: snapshots no longer store outputs that can be computed again exactly from a block's state (checked bit for bit when the snapshot is taken) or that copy it. Gray–Scott's snapshots are 72% smaller (the two state grids alone), so it can rewind about four times as far back at full detail.
- Long runs of large grid models no longer use unbounded memory: recorded grids keep about 256 MB (thinning sooner for big grids) and rewind points about 256 MB, both thinned when full, so rewind becomes coarser rather than memory running out.
- Unit conversions and input blocks are labelled Quantitative, not Verified (ADR 0061): Verified is earned by a run of a model through a convergence check (planned), never declared by a method.
- Typed equations run faster: they are compiled to an instruction list when the model loads (ADR 0060), taking about 40% less time per step (the Lorenz system: 1.8× the built-in block's time, from 3.1×).
- A parameter changed while running now acts in the next step; before, a change to a block feeding others reached them one step later.
- Units are shown with a slash: `m/s`, `kg·m/s^2`, `1/s` instead of `m·s^-1`.
- The inspector lists starting values last, each marked ↻, without the "starts at" and "used by" lines; hover a name to see which formulas read it. The "Unit conversions" section moved into each conversion block's entry.
- The log lists the newest message last.
- Values that formulas set no longer appear on diagram nodes; the global "Values" switch is replaced by each node's own toggle.
- Blocks fuse by the method they actually run: a block that leaves its method out (its type's default) now fuses with a connected block that names the same method and options, e.g. `rk4` with one substep.
- Formula blocks and unit conversions join the fused group they connect (ADR 0051): a conversion or a promoted filter between two blocks solved together no longer splits them, and a formula driving a fused block is evaluated at every solver stage. Results of such models change slightly (more accurate).
- Block and subsystem port places are written `canvas`, like filters' and views' (ADR 0052); files with `at` still open, and the log says it was converted. Python `Model.add_block` takes `canvas=`.
- Connections need the same unit at both ends (ADR 0045): a `cm` output no longer feeds an `m` input silently; put a `units.convert` block between them. The cruise-control example now gives its equations units.
- The CLI needs Rust 1.95 (it renders views with egui).
- The simulation runs on its own thread (ADR 0035): the window stays responsive during slow steps and large sweeps, which are evaluated in the background with progress and restarted by any change; a step running longer than half a second is shown in the toolbar. Sliders apply while dragged only for real-time models; for others the parameter's field shows the pending value in the warning colour while dragging, and it applies on release (ADR 0037).

- Sweeps moved from `controls.sweep` to the top-level `sample` section (ADR 0027); old files are converted on load: views bound to `t` are bound to the first swept parameter, two-parameter heat maps and cut filters to the `grid.` signals. A one-parameter sweep is indexed by sample number, with the parameter as a signal.
- `plot.profile` draws line fields only; cuts through 2D grids come from cut filters (ADR 0031, superseding ADR 0029's cuts inside the profile).
- Filters (ADRs 0030–0032): `controls.filters` holds named filters that name their inputs; `expression` filters are derived signals (they may now use each other) and `cut` filters cut 2D grids along x, along y or free lines into line fields with a coordinate and readable labels. The "Signals…" window becomes "Data…", listing and editing all filters; a new cut filter opens a profile of its cuts. Older `controls.signals` and profile cut selections are converted on load.
- `plot.xy` (plots against time, phase portraits) has a "swap axes" button: the same signals drawn transposed, saved with the view.
- Profile cuts (ADR 0029): `plot.profile` draws 2D grids as straight cuts in any direction, against fraction along the cut, x, y or distance, with bilinear or nearest interpolation; cuts are saved in the view's new `selection` and edited in the side panel. The resonance-map example adds resonance curves at four dampings.
- Heat map axes (ADR 0024): `x` and `y` each take `t` or a coordinate of the field (declared by its block, e.g. `rod.position`, or a swept parameter); pickers list only those; a "swap axes" button; unevenly spaced coordinates are drawn correctly. Files with the old `position` and `time_axis` are converted on load.
- View settings and slots are shown only where they apply (ADR 0025): e.g. `trail_length` is hidden and ignored in sweeps.
- `PortSpec::coordinate_of` declares an output a coordinate of another.
- Two-parameter sweeps (ADR 0022): `controls.sweep` may list two parameters; every output and derived signal becomes a grid over both, shown by a heat map placed by the parameter values; "+ parameter" and × in the app's sweep bar; heat maps gain `x`/`y` coordinate slots for 2D grids and a `log_colour` style property; resonance-map example.
- Plots span at least a millionth of the largest value shown, so a conserved quantity draws flat instead of magnifying rounding noise into apparent drift (zooming in still works).
- App: messages go to a log: a tile left of the rewind bar shows the newest one (dimmed after 8 s) and opens the full list, so messages never resize the window; the model description is one line with the full text on hover (one tooltip); the Derived signals text boxes are wider.
- App: "More views…" lists only views that apply to the model; saved 3D cameras are written in short form (0.35, not 0.3499999940395355).
- Views: `plot.time` and `plot.phase` are merged into `plot.xy` (any signals against time or each other, several curves, trail length as a scrolling window against time); "More views…" lists presets ("Plot against time", "Phase portrait", "3D trajectory"); files with the old types are converted on load (ADR 0018).
- Block factories receive a `BlockConfig` (method plus definition lines) instead of method settings alone.
- App: the view selector buttons are replaced by tiles and "More views…"; `--view` opens only that view.
- App: the phase portrait fades its trail by time, like the 3D view; the axis pickers became slot pickers.
- App: the File path field is replaced by the file dialogs; the current file's path is shown in the toolbar.
- App: the scroll wheel zooms 2D plots around the pointer instead of panning.
- `ParamSpec::min`/`max` renamed to `suggested_min`/`suggested_max`; the range is a hint for sliders, not a limit. `set_param` rejects only NaN and infinite values (`SimError::InvalidParam`); unknown names return `SimError::UnknownParam` instead of `SimError::BadConnection`.
- Snapshots store parameter values; `Simulator::restore` rewinds them along with state.
