# Changelog

All notable user-visible changes are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/) once it reaches 0.1.0.

## [Unreleased]

### Added

- Probes on the diagram (ADR 0062): "Add probe" in the Diagram's menu adds a probe node; drop outputs or filter outputs on its `record` input to record them, delete a wire to stop. Double-click it to set when it records, how long it keeps samples and its file. Changes apply without restarting the run, and undo works as for filters and views. Runs › "Save probe data" writes the probes' files beside the model. A view can show what a probe recorded instead of every step: choose it in the view's "from" menu (saved as `probe` in the view).
- Probes in model files (ADR 0062): `controls.probes` entries record chosen signals and fields (`"record": ["gs.v"]`), every N steps, every Δt of simulated time or at listed times (`"every": {"seconds": 50}`), keep them thinned, the newest N or all (`"keep": {"last": 100}`), and can write files (`"to": "pattern.csv"`): a CSV of time and signals, and a NumPy `.npy` file per grid or point field beside it. `simsandbox run FILE --probe NAME` prints one probe; `--save-probes DIR` writes the probes' files. Python: `Model.add_probe` and `Model.run_probes(save=...)`. A probe with bad settings is dropped with a warning; the file still opens.
- Example "Gray–Scott spots (reaction–diffusion on a 2D grid)": two chemicals on a 128 × 128 periodic grid; from two seeds, spots grow and split. Sliders for F and k change the pattern.
- 2D grids in typed equations: two `grid` lines make a grid, arrays are written `T[x, y]`, `lap(T)` sums the second derivatives along both axes, `ddy(T)` differentiates along y, edges are set per axis (`edge T: x periodic, y- = 0`), and `at(T, i, j)` reads one cell. The heat map shows them with both axes as coordinates.
- Implicit methods `trbdf2` (second order) and `backward_euler` (first order) for stiff systems such as diffusion on fine grids: they stay stable at steps far beyond what `rk4` allows (a 0.05 s step of an 800-cell rod takes 0.25 ms instead of 5 ms with the substeps RK4 needs). Every continuous block and fused group can use them, and runs still replay exactly after a rewind.
- Example "Typed heat equation (arrays on a grid)": the heat rod in four lines of typed equations, verified against the exact solution of the heat equation.
- Arrays in typed equations (ADR 0060). Declare a line of cells with `grid x [m] = 0 .. length, 50`; then `state T[x] [K] = expression` has a value per cell, and `dT/dt = alpha*lap(T)` is the heat equation. Set the ends with `edge T: x- = left, x+ gradient = 0` or `edge T: x periodic` (insulated if not given). `lap(T)` and `ddx(T)` are stencils; `sum`, `mean`, `minof`, `maxof` and `at(T, i)` give one value; `spacing(x)` is the cell width. Arrays are grid outputs with the axis as their coordinate, so the heat map and profile views show them, and `input q[x]` takes a grid from another block. Units are checked throughout. A typed heat rod runs as fast as the built-in one.
- Inputs (ADR 0058): `input.value` and `input.pointer` blocks are values set from outside a running model, wired like any block (settings `unit`, `min`, `max`). Bind them in `controls.inputs`: two keys drive a value (`{"driver": {"keys": ["ArrowDown", "ArrowUp"]}}`, optionally at a `rate` per second), and a view feeds a pointer (`{"hand": {"view": 0}}`): pressing on `plot.xy` or the pendulum view then sends `x`, `y` and `down` instead of panning. New examples: "Drag the bob" and "Steer the car with keys". `plot.xy` has two new styles: `reach` (always show at least that far either side of 0) and `equal_scales`.
- Every change made during a run (keys, pointer, sliders, typed values) is recorded at a step boundary. After a rewind, running on replays it exactly ("Replaying input" in the toolbar); new input from then on starts a new branch. `run.inputs` in the model file is a default schedule of changes (`{"t": 5, "set": "push.y", "to": 40}`) applied in every run.
- Run files (ADR 0059): Runs ▸ "Save run…" writes `<model>.<run>.run.json` beside the model with the run's schedule, recorded input, seed, settings and the model's hash. The Runs menu replays a saved run (warning if the model changed since) and can make a run, or the current one, the model's schedule. Opening a run file (or dropping one on the window) replays it.
- Headless inputs: `simsandbox run RUN.run.json` replays a run; `run` and `render` take `--inputs RUN` to apply a run's events to a model; `simsandbox check` checks run files (missing model, changed model, unknown keys) and `simsandbox schema run` prints their schema. Python: `Model.run(inputs=[(t, key, value), ...])` or a `Run`, `Model.schedule(t, key, value)`, and `ss.Run` (`load`, `replay`, `save`).

- Formulas in the app: type `= expression` into any value field (for example `= 2*kp`) to compute it from the model's parameters; a computed value shows its formula and can be changed, or replaced by typing a number. The inspector's Model group declares new parameters ("+ parameter": name, value, unit) and removes them (right-click). A formula or parameter that would stop the model loading is refused with the reason.
- Which nodes on the diagram show their values is saved with the model, and headless diagrams follow it; `simsandbox render --diagram --values` (Python: `render(diagram=True, values=True)`) shows them all.
- Blocks inside a subsystem show their values: the default every use takes unless it sets its own (marked `*`).
- The Controls show each slider's range ends beside it, editable in place.
- A Controls pane (ADR 0054): pin any value with 📌 in the inspector (or right-click its name) to keep it there; a pinned value can have a slider, whose range you set by right-clicking its name. Click 📌 again to unpin. Files whose values have sliders open with them pinned.
- Nodes on the diagram open and close their values with a triangle in their header. Conversion blocks show their units beside their ports; double-click one to change it.
- Selecting several blocks shows each in the inspector. Blocks added on the diagram that cannot run yet (for example a conversion with nothing wired in) show in the inspector as "not running yet", and their values and units can be set there or on their nodes.
- Click a curve in a plot to select where it comes from: its block (or subsystem use) is shown in the inspector and selected on the diagram.
- Values on the diagram (ADR 0053): blocks and subsystem uses show their parameter values under their ports; zoom in and double-click a value to type a new one, applied at once. "Values" in the Diagram toolbar hides them; they also hide when zoomed out.
- Inspector (ADR 0053), replacing the parameter panel: a search box; Controls (parameters with sliders, and any you pin by right-clicking a name); what you select on the diagram; the model's own parameters; one table per subsystem used several times, a column per use, with "Set every use"; each block's parameters with starting values last. Values set by formulas are listed once, at their source ("used by 3"); tick "computed" to see them all. "Solving…" moved to the toolbar, and each view's style to its "style" menu.
- Dockable tabs (ADR 0053): the inspector, the diagram and the views are tabs you can drag, stack and split. Each view can have a tab of its own ("own tab") or be tiled with others ("tile"); right-click a tab to "Pop out" into its own window. "More views…" and "Data…" moved to the toolbar. The arrangement is saved with the model (`controls.layout`), and `simsandbox render` draws the views as it places them.
- Data layer on the canvas (ADR 0050): the Diagram tab shows filters and views as dashed nodes, wired by dashed wires from the signals they read. Drop an output on a view's slot to show it there, delete a data wire to stop, add, rename, move and delete filters and views, double-click to edit a filter or show a view: all without restarting the run. "Hide data" hides the layer. A filter dropped on a block input is refused, with "Promote and connect": promoting turns an expression filter into a formula block that runs with the model (Python `Model.promote`). Places are saved as `canvas` on filters and views; `simsandbox render --diagram` draws the layer (`--no-data` to leave it out).
- Undo and redo for canvas edits (ADR 0050): buttons, Ctrl+Z and Ctrl+Shift+Z (or Ctrl+Y); parameter values changed since an edit are kept when undoing it.
- Units in typed equations (ADR 0045, ADR 0049): write a unit in brackets where a name appears, `input F [N], v [m/s]`, `param m [kg] = 1000`, `state v [m/s] = 0`, or at the end of an equation for its left side, `E = m*v^2/2 [J]`, `dv/dt = (F - c*v)/m [m/s^2]`. Then every line is checked and a line that does not balance is an error naming both units; names without a unit are dimensionless, and equations without any unit behave as before. Typed blocks with units connect to built-in blocks such as the coupled oscillator. `param NAME = value` gives a parameter its default, and `state x = value` declares a state with its initial value (the default of `x0`); "New model…" starts with its states declared.
- More units (ADR 0047): SI prefixes on SI units (`kN`, `MPa`, `µs`, `mL`, `kWh`), common units (`min`, `h`, `d`, `L`, `t`, `bar`, `atm`, `eV`, `cal`, `deg`, `rpm`, `%`, `ppm`) and US/imperial units at their exact definitions (`in`, `ft`, `yd`, `mi`, `nmi`, `kn`, `mph`, `lb`, `oz`, `lbf`, `psi`, `gal`, `hp`, `BTU`, `slug`). Units may use parentheses (`N/(m*s)`) and number factors (`0.3048*m`), and every unit SimSandbox shows can be typed back. `simsandbox describe units` (Python `describe("units")`) lists them all. `°C` and `°F` are refused with the reason (use K), and `a/b*c` is refused as ambiguous.
- Units of model and subsystem parameters are checked (ADR 0046): a declared `unit` must be a unit, and a formula using parameters with units must balance and give the unit of what it sets; it is computed in SI, so a model parameter of 2 km sets a length in m to 2000. Formulas without units, and those setting blocks that give no units, work as before. The platoon example now has units throughout.
- `units.convert` block (ADR 0045): converts a signal between units of one kind of quantity (settings `from` and `to`, e.g. `mm` to `m`); edit its units in the side panel; the diagram shows `from → to`. Units example: a shaker in millimetres drives springs in metres, and one spring is plotted in centimetres. Blocks have an optional `settings` section, and `method` may be left out. Python `Model.add_block(..., settings={...})`.
- Unsaved changes (ADR 0044): before opening another model or example, applying a new model or closing the window, the app asks to save changes a save would write (parameters, edits, sliders, views, speed); the toolbar shows "● unsaved".
- Older files (ADR 0044): files in older forms of the format still open, and the app's log and `simsandbox check` say what was converted; saving writes the current form. `simsandbox upgrade FILE` and Python `simsandbox.upgrade` write a file in the current form. A file from a newer SimSandbox, or with an unknown field, gets a message saying so.
- Subsystems and model parameters (ADR 0043): a model file can declare its own parameters (`params`) and define subsystems (`subsystems`: blocks, wires, parameters, inputs and outputs) used like block types by name, any number of times; any block parameter can be a formula of the parameters in scope (`"m": "mass"`, `"K": "2*capacity"`). One slider then sets every block that uses a parameter: the grazing example's field size is now one model parameter. On the canvas, double-click a subsystem to edit its inside (every use changes), add and rename its ports, select several blocks with Shift-click or a Shift-drag box and make a subsystem of them. The side panel shows the model's parameters, each use's, and values formulas set. `simsandbox check` lists subsystems and formulas; `simsandbox render --diagram --subsystem NAME`; Python `Model.declare`, `Model.group` and formulas in `Model.set`. Platoon example: one follower subsystem used three times.
- Node canvas (ADR 0042): a Diagram tab beside Views shows the model's blocks, ports and wires; drag blocks, draw wires from outputs to inputs, drag a wire off an input to remove it, add blocks by type, rename and delete them, and double-click to edit equations. Positions are saved in the file (`canvas` per block, ADR 0052); blocks without one are laid out by signal flow. Edits restart the run once the model loads; until then they wait as a draft with the reason, and the run goes on.
- "Start from here": the current state becomes where the run starts, saved with the model (initial-condition parameters such as `v0`, or a `start` entry with a block's state and table rows), e.g. to study a transient from a steady state; "Forget start state" undoes it. Headless: `simsandbox start-from FILE --t T` and `Model.start_from(t)`.
- `simsandbox render --diagram` and `Model.render(diagram=True)` draw the block diagram; `Model.add_block(..., canvas=(x, y))`.
- Headless interface for people and AI agents (ADRs 0039, 0041; [guide](docs/guides/headless.md)): `simsandbox describe [TYPE]` lists every block, view and filter type with ports, units, parameters, methods and labels as JSON; `simsandbox schema` prints the file's JSON Schema; `simsandbox check FILE` reports every problem with its path or line and column, plus parameters and what the model records, as JSON (exit status 1 if it cannot run); `simsandbox run --format json` writes outputs grouped by port, including populations; `simsandbox render FILE --out IMAGE.png` draws the model's views as the app shows them, without a window or GPU.
- Python package `simsandbox` (`pip install ./python`): describe, check, build (`Model.add_block`, `connect`, `set`, `sweep`, `set_run`), run (results as numpy arrays) and render models; errors raise `ModelError` with every problem found.

- Direct feedthrough and algebraic loops (ADR 0040): outputs may depend on inputs at the same instant (declared per output and input), so chains such as sensor → controller → actuator agree without a step's delay, also inside blocks solved together; loops of such outputs are found when a model opens, named in the log and by `simsandbox run`, and solved by Newton's method unless `run.loops` says `fixed_point` or `refuse`. Typed equations take `input u, F` lines. Cruise-control example.
- The agent domain and the grazing model (Phase 1 gate): `agents.grazers` (animals that wander, eat grass, breed and die, competing in an update order chosen per block: `random_order`, `synchronous` or `id_order`, saved as `update` and chosen in the side panel), `eq.grass` (grass regrowing on a 40 × 40 field), a heat map `points` slot to draw animals over their field, and the grazing example.
- Kernel support for populations (ADR 0034): Blocks can keep tables of rows with stable ids that grow and shrink, saved in snapshots and rewound like other state; population ports carry a varying number of points between Blocks; `run.seed` in model files seeds counter-based random numbers, so the same file gives the same run. The point-set view draws populations.
- ADRs 0037 (sliders live only for real-time models), 0038 (Phase 1 revised; user-defined blocks decided later) and 0039 (AI agents as first-class users, also in the vision and `AGENTS.md`).
- ADRs 0035 (the simulation moves to a worker thread) and 0036 (Python-defined blocks in Phase 1; revised Phase 1 order).
- ADR 0034: the agent domain (populations as kernel-owned tables without a capacity limit, variable-length point sets, per-block update order, counter-based randomness from `run.seed`).
- ADR 0033: Phase 1 order and scope (agent domain and the grazing model first, then direct feedthrough, node canvas, subsystems, headless Python API).
- Surface and contour views: `plot.surface` shows a grid field as a rotatable, shaded 3D surface over its axes and `plot.contour` as lines of equal value (`levels`, `log_scale`); both work on two-parameter sweeps and on lines of cells over time (e.g. the heat rod). The resonance-map example adds a surface.
- Sweeps as samples (ADRs 0027–0028): a top-level `sample` section with designs `grid`, `list`, `random`, `latin_hypercube` and `sobol` over any number of parameters (seeded, at most 250 000 samples); every sample is recorded with the swept parameters as signals, a two-parameter grid also as `grid.<signal>` grids for heat maps and cuts, and unordered samples are drawn as markers coloured by value; the app's sweep bar chooses the design, count, seed and parameters; `simsandbox run` writes one row per sample; resonance-samples example (a Sobol sweep).
- Documentation system: `AGENTS.md` entry point and session protocol, documentation map, status, vision, roadmap, architecture, design, guides, research, open questions, risks, glossary, session notes, ADRs 0005–0006.
- Docs check (`scripts/check_docs.py`) in CI; pull request and issue templates.
- `Model::param`, `Model::params`, `Model::block_ids`, `Simulator::model` and `Simulator::param` for reading parameters and Block specs.
- ADRs 0007 (JSON model files with a block-type registry), 0008 (all-native egui + wgpu desktop UI), 0009 (hobbyists are the first audience), 0010 (wall-clock pacing of the live loop), 0011 (typed parameter entry; ranges are suggestions), 0012 (exploration controls saved in model files), 0013 (run settings in a `run` section), 0014 (opening view saved in `controls`), 0015 (pluggable views; which style options to expose), 0016 (models choose the views shown) 0017 (built-in expression parser for typed equations), 0018 (one x–y plot), 0019 (typed models without time), 0020 (method choice only for approximations) and 0021 (maps, formulas and sweeps).

- Model files (format 1): JSON with blocks, connections and optional `controls`; `simsandbox-file` crate with `load`, `ModelFile::to_json` and `ModelFile::capture_params`; JSON Schema in `crates/simsandbox-file/model.schema.json`.
- Block-type registry (`simsandbox_core::registry`) and `simsandbox_eq::register` with `eq.lorenz` and `eq.coupled_oscillator`; `Integrator::from_settings` and `Integrator::settings`.
- `simsandbox run FILE [--t-end] [--dt]` writes every output of a model file as CSV.
- Example files `examples/lorenz.ssbx.json` and `examples/coupled-oscillators.ssbx.json`.

- App: parameter panel (typed entry with units, initial-condition markers, opt-in sliders with editable ranges), Restart from current parameters, Save, pause at the file's `t_end`.
- Model files: optional `run` section with `dt` (default 0.01) and `t_end` (ADR 0013); `simsandbox run` uses it unless `--dt`/`--t-end` are given.

### Fixed

- Turning off a slider in a model saved before pins (such as the platoon) also unpinned the value. Such files now get their pins when opened, reported as a conversion.
- A popped-out tab froze the main window while the main window had focus (Linux): popped-out tabs now draw on their own.
- Turning the only plot into a tab of its own no longer removes the Views tab, so the plot can be tiled back after closing its tab.
- Popping out a tab no longer waits for vsync, which could stall the main window on Linux (Wayland).
- A value typed on a block that was not running yet was ignored; it now goes into the pending edits.
- An arrow that the app's font lacks showed as a box in conversion labels and some messages.
- Numbers in model files are read back exactly as written; before, some values came back one unit in the last place off, so a saved model could differ slightly from the one that was saved.
- App: a sweep that reaches an infinite value (the resonance example swept over `spring.c` from 0) no longer crashes; plots leave a gap at infinite or NaN values. Choosing a sweep parameter uses its slider range when it has one.

### Changed

- Long runs of large grid models no longer use unbounded memory: recorded grids keep about 256 MB (thinning sooner for big grids) and rewind points about 256 MB, both thinned when full, so rewind becomes coarser rather than memory running out.
- Unit conversions and input blocks are labelled Quantitative, not Verified (ADR 0061): Verified is earned by a run of a model through a convergence check (planned), never declared by a method.
- Typed equations run faster: they are compiled to an instruction list when the model loads (ADR 0060), taking about 40% less time per step (the Lorenz system: 1.8× the built-in block's time, from 3.1×).
- A parameter changed while running now acts in the next step; before, a change to a block feeding others reached them one step later.
- Units are shown with a slash: `m/s`, `kg·m/s^2`, `1/s` instead of `m·s^-1`.
- The inspector lists starting values last, each marked ↻, without the "starts at" and "used by" lines; hover a name to see which formulas read it. The "Unit conversions" section moved into each conversion block's entry.
- The log lists the newest message last.
- Values that formulas set no longer appear on diagram nodes; the global "Values" switch is replaced by each node's own toggle.
- Blocks fuse by the method they actually run: a block that leaves its method out (its type's default) now fuses with a connected block that names the same method and options, e.g. `rk4` with one substep.
- Formula blocks and unit conversions join the fused group they connect (ADR 0051): a conversion or a promoted filter between two blocks solved together no longer splits them, and a formula driving a fused block is evaluated at every solver stage. Results of such models change slightly (more accurate).
- Block and subsystem port places are written `canvas`, like filters' and views' (ADR 0052); files with `at` still open, and the log says it was converted. Python `Model.add_block` takes `canvas=`.
- Connections need the same unit at both ends (ADR 0045): a `cm` output no longer feeds an `m` input silently; put a `units.convert` block between them. The cruise-control example now gives its equations units.
- The CLI needs Rust 1.95 (it renders views with egui).
- The simulation runs on its own thread (ADR 0035): the window stays responsive during slow steps and large sweeps, which are evaluated in the background with progress and restarted by any change; a step running longer than half a second is shown in the toolbar. Sliders apply while dragged only for real-time models; for others the parameter's field shows the pending value in the warning colour while dragging, and it applies on release (ADR 0037).

- Sweeps moved from `controls.sweep` to the top-level `sample` section (ADR 0027); old files are converted on load: views bound to `t` are bound to the first swept parameter, two-parameter heat maps and cut filters to the `grid.` signals. A one-parameter sweep is indexed by sample number, with the parameter as a signal.
- `plot.profile` draws line fields only; cuts through 2D grids come from cut filters (ADR 0031, superseding ADR 0029's cuts inside the profile).
- Filters (ADRs 0030–0032): `controls.filters` holds named filters that name their inputs; `expression` filters are derived signals (they may now use each other) and `cut` filters cut 2D grids along x, along y or free lines into line fields with a coordinate and readable labels. The "Signals…" window becomes "Data…", listing and editing all filters; a new cut filter opens a profile of its cuts. Older `controls.signals` and profile cut selections are converted on load.
- `plot.xy` (plots against time, phase portraits) has a "swap axes" button: the same signals drawn transposed, saved with the view.
- Profile cuts (ADR 0029): `plot.profile` draws 2D grids as straight cuts in any direction, against fraction along the cut, x, y or distance, with bilinear or nearest interpolation; cuts are saved in the view's new `selection` and edited in the side panel. The resonance-map example adds resonance curves at four dampings.
- Heat map axes (ADR 0024): `x` and `y` each take `t` or a coordinate of the field (declared by its block, e.g. `rod.position`, or a swept parameter); pickers list only those; a "swap axes" button; unevenly spaced coordinates are drawn correctly. Files with the old `position` and `time_axis` are converted on load.
- View settings and slots are shown only where they apply (ADR 0025): e.g. `trail_length` is hidden and ignored in sweeps.
- `PortSpec::coordinate_of` declares an output a coordinate of another.
- Two-parameter sweeps (ADR 0022): `controls.sweep` may list two parameters; every output and derived signal becomes a grid over both, shown by a heat map placed by the parameter values; "+ parameter" and × in the app's sweep bar; heat maps gain `x`/`y` coordinate slots for 2D grids and a `log_colour` style property; resonance-map example.
- Plots span at least a millionth of the largest value shown, so a conserved quantity draws flat instead of magnifying rounding noise into apparent drift (zooming in still works).
- App: messages go to a log: a tile left of the rewind bar shows the newest one (dimmed after 8 s) and opens the full list, so messages never resize the window; the model description is one line with the full text on hover (one tooltip); the Derived signals text boxes are wider.
- App: "More views…" lists only views that apply to the model; saved 3D cameras are written in short form (0.35, not 0.3499999940395355).
- Views: `plot.time` and `plot.phase` are merged into `plot.xy` (any signals against time or each other, several curves, trail length as a scrolling window against time); "More views…" lists presets ("Plot against time", "Phase portrait", "3D trajectory"); files with the old types are converted on load (ADR 0018).
- Block factories receive a `BlockConfig` (method plus definition lines) instead of method settings alone.
- App: the view selector buttons are replaced by tiles and "More views…"; `--view` opens only that view.
- App: the phase portrait fades its trail by time, like the 3D view; the axis pickers became slot pickers.
- App: the File path field is replaced by the file dialogs; the current file's path is shown in the toolbar.
- App: the scroll wheel zooms 2D plots around the pointer instead of panning.
